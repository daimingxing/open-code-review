# 项目设计

本文件维护基于 Alibaba OpenCodeReview（OCR）二次开发的项目定位、共同设计原则与扩展边界，适用于当前及后续功能。具体功能需求与验收由各自 Spec 维护；这里不复制命令参数、文件格式或开发进度。更新日期：2026-09-30。

## 项目定位

在上游 OCR 的基础上建设可复用、可持续维护的智能审查能力。产品提供通用能力，具体组织、项目与框架的审查标准由外部资料配置，不将某个业务项目的规则硬编码为全局默认行为。

当前从本地 CLI 能力开展二次开发，再考虑界面层。后续界面复用相同的规则、知识关联和核心能力；是否增加新的运行方式或功能，由对应 Spec 明确范围。

## 兼容与复用

- 保留原生命令、参数、默认值和输出语义。新增功能有明确入口；未启用时保持原有行为，不能占用既有参数来表达另一种含义。
- 先核实上游能力，再决定扩展位置。优先复用现有规则解析、模型配置、Git 范围选择、MCP 接入及结果能力；确认存在缺口后才增加必要代码。
- 命令风格与既有用法一致，功能契约明确输入、输出、默认行为、失败与兼容边界；计划接口和已验证能力分别标明。
- 保持便于上游同步的职责边界。分支、冲突和发布流程统一见[分支维护](branch-maintenance.md)，不在功能设计中另立一套流程。

## 外部资料与能力边界

- 审查规则和知识资料外置，便于复用及统一管理。资料关联与访问授权各有职责，规则中声明路径不等于获得访问权限。
- 外部内容按用途提供：规则表达标准，背景表达当次需求，知识提供参考依据。采用全文提供还是按需读取，由具体功能结合资料规模及能力证据决定。
- 不把某个参考 Skill 的执行步骤、脚本或输出格式直接当作产品默认流程；提取适用需求，并在功能 Spec 中明确承接范围。
- 新功能沿用现有配置入口；只有已有方式无法表达需求时才引入新协议或管理机制。界面与 CLI 应共享同一套能力契约和资料关联。

## 事实、模型与可靠性

- 区分确定性事实、模型判断、未验证内容和展示表达。事实保留来源、范围与适用版本；缺失或未执行不能展示为零问题或已通过。
- 代码证据对应实际审查范围，历史版本与当前工作区不混用。引用外部知识时区分“读取成功”和“正确应用”。
- 数量、标识、状态等可确定内容优先由程序处理；模型承担需要理解或表达的工作，具体可访问资料和可修改内容由功能契约限定。
- 输入校验、访问边界和数据保护随功能首次交付。新增阶段失败应保留已有有效成果，明确失败阶段与限制；覆盖、重试及退出行为在 Spec 中规定。
- 模型调用有可观察的用量与失败结果，需要修复循环时设置次数或预算边界。验证工具调用不替代验证实际业务效果。

## 开发与演进

以可独立验证的用户行为拆分工单，按真实依赖推进；每张工单包含对应测试与必要说明。优先选择已有能力和最小可用改动，不为假设中的扩展提前建立抽象或管理系统。

功能验收关注用户可观察的行为和交付结果。模型效果需要真实样例验证，受控模型用于稳定覆盖命令、数据和失败路径。具体测试边界、阶段顺序与完成条件在各功能 Spec 及工单中明确。

## 后续演进想法

2026-10-10：当前审查与报告功能由用户验证后，再考虑将知识读取服务随产品交付。用户可以自行安装 Node.js，但不应再单独安装文件 MCP 服务或编辑 MCP 配置；产品负责携带服务及运行依赖、定位与启动、读取工具限制，用户只需指定授权知识库目录，审查规则继续提供阅读指引。

倾向复用现有 MCP 接入与知识来源记录，随产品固定服务版本并保留许可证。npm 产品包可通过依赖自动安装服务，独立发布包可随附服务文件；用户现有外部 MCP 配置应继续兼容。

这是待完善的产品化想法，尚未实现。知识库配置入口、目录授权方式、发布形式、Node.js 版本要求与升级策略等，在下一阶段另写 Spec 时细化，不纳入当前功能验收。

## 文档职责

需求、设计、测试和验收信息的权威归属如下。

| 文档 | 权威内容 |
|---|---|
| 本文件 | 项目级定位、共同原则与扩展边界 |
| [领域术语](../GLOSSARY.md) | 统一概念定义 |
| ADR | 已接受的重要架构选择、理由与代价 |
| `.scratch/<feature>/spec.md` | 单项功能的需求、行为、默认值、范围和验收标准 |
| 功能工单 | 可执行交付、前置依赖、验收证据与讨论 |
| [OCR 知识库](open-code-review/README.md) | 原生能力、集成限制、版本和验证证据 |
| [审查资源](review-resources.md) | 测试仓库、参考 Skill 与知识库的长期地址 |
| [人工验收材料](mock/README.md) | 产品验收脚本、稳定测试输入和结果判定的归属 |
| [开发复测记录](retests/README.md) | 开发回归与故障复现命令、环境前提和实测证据的归属 |

详细行为只在对应 Spec 维护，工单引用它并列明本次交付；宏观原则变化才修改本文件。ADR 保留决策背景，改变既有选择时标明被哪项新决策替代，不将实施进度混入决策状态。文档移动或职责变化时同步入口链接。
