# 项目设计

本项目基于 OpenCodeReview（简称 OCR）二次开发，提供可配置审查规则、框架知识和自定义 HTML 报告的通用代码审查工具。先实现核心审查与报告能力，再增加本地 Web 界面，方便没有开发经验、不熟悉命令行的用户使用。

本文记录已确定的开发方向、功能目标与待细化事项，不代表功能已经实现。OCR 的上游能力见 [知识库](open-code-review/README.md)，分支与上游同步流程见 [分支维护规则](branch-maintenance.md)。

## 产品范围

- 在本地运行，使用用户已准备好的 Git 仓库。用户自行处理认证、拉取及分支同步。
- 首版以两个已有分支的变更审查为范围，暂不扩展提交号或时间范围选择。
- 一个业务项目可关联前端、后端等多个仓库，各仓库分别选择基准分支和目标分支。
- 审查规则、框架知识和报告要求可自定义，支持不同业务项目使用不同资料。
- 报告面向人的阅读，支持自定义内容组织、章节和样式，不要求以 Markdown 作为中间产物。

## 技术路线与开发顺序

### 核心能力

在 OCR 中新增独立的报告生成命令，尽量复用其审查、模型接入、配置和会话读取能力，保留原有命令与行为。扩展尽量使用独立模块，必要时再修改上游已有代码。

报告生成的优先实现方向是：程序整理最终审查结果和 Git 数据，模型根据报告要求生成 HTML，程序负责保存和必要检查。先验证直接生成 HTML 的效果，再决定是否需要分段生成、文件编辑或局部修改工具，不预先引入完整通用 Agent。

不以修改原有审查 JSON 或提示词为前提；根据实际报告所缺的信息，再决定补充数据、增加分析步骤或扩展输出。

### 本地 Web 界面

核心功能基本实现后，再增加本地 Web 界面。前端优先采用开发者熟悉的 Vue.js，提供仓库、分支、审查方案和报告的可视化操作，减少用户手写命令与文件路径的负担。

界面复用核心能力，不另做一套审查逻辑。本地服务如何连接 OCR、进度如何传递、配置如何保存，留待界面阶段细化。

## 外部资料与审查方案

产品代码负责读取资料、执行审查和生成报告。具体框架知识、项目专属规则及报告要求保存在外部文件中，通过配置引用，不作为产品源码的一部分。

资料可以独立更新；更换审查项目时，更换关联配置与资料，不需要修改或重新发布产品。

审查方案关联审查规则、框架知识和报告要求。本次业务背景用于说明变更目标、预期行为和相关约束。知识库以 Markdown 为主，规模可控时可一次性提供相关内容，当前不要求复杂的动态知识检索。

## 用户操作流程

1. 选择业务项目，登记参与审查的本地仓库。
2. 为各仓库选择基准分支和目标分支。
3. 选择审查方案，关联外部资料并补充本次业务背景。
4. 开始审查，查看各仓库进度与完成情况。
5. 生成、阅读和导出 HTML 报告。

该流程是核心能力与后续界面的共同目标，具体页面和交互尚未设计。

## 报告内容与数据边界

报告应能超出问题列表，按要求组织以下内容；并非每份报告都必须包含全部章节：

- 项目、仓库、比较范围、审查状态与覆盖情况。
- 文件数、增删行、提交数、参与人员等变更统计。
- 风险摘要、问题明细、代码位置、影响与修复建议。
- 模块成果、个人工作明细、代表提交及问题关联人员。

最终问题和运行状态来自 OCR，提交与变更统计由 Git 补充。业务成果与综合风险等需要理解代码的内容，可由模型结合材料分析；不能将缺失数据当作已知事实。

报告数据需区分以下含义：

- 变更范围与实际审查范围不同，选中任务全部完成不等于所有变更都已审查。
- Git 作者、提交者和远端推送者不同，本地 Git 记录不能直接证明谁“上传”代码。
- 问题关联修改者不等于认定缺陷责任人，多人修改、跨文件及删除代码等情况应保留不确定性。
- 增删行、提交数是变更量，不代表工时或绩效；最终差异与逐提交累加的口径不同，个人文件数也可能重叠。
- 多仓库报告汇总不等于跨仓库联合语义审查，例如前后端接口一致性检查需要另行设计。

## 待细化事项

- 独立报告命令的输入、输出及失败重试方式，是否支持仅调整要求后重新生成报告。
- 报告要求的文件格式、参考 HTML 的使用方式，以及长报告和输出完整性的处理。
- 人员关联、变更统计和业务总结的具体口径与所需材料。
- 多仓库合并报告的组织方式，以及是否纳入首次可用版本。

## 后续扩展方向

- 若需要完整通用智能体的持续对话、调查和文件编辑能力，可考虑 [Pi](https://github.com/earendil-works/pi)；当前不引入。
- MCP 可用于知识查询等工具补充，不作为自定义报告生成的主要路线。
- 报告形式稳定后，可考虑代码模板或模型与模板结合，降低重复生成成本。
- 有实际需要时，再考虑桌面客户端或在线部署。
