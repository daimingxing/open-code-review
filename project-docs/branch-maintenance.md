# 分支维护规则

本文规定 OpenCodeReview 二次开发仓库的分支职责、上游同步、冲突处理和发布维护方式。产品需求与功能方案见 [项目设计](project-design.md)。本文不代表相关分支或远程仓库已经创建。

## 分支职责

| 分支 | 来源与职责 | 保留方式 |
|---|---|---|
| `main` | 跟踪用户选定的上游正式版本，不加入我们的功能改动 | 长期保留 |
| `dev` | 集成上游能力和我们的扩展，保持可运行 | 长期保留 |
| `feature/<功能>` | 从 `dev` 创建，开发具体功能，验证后合回 `dev` | 合并后允许保留，由用户确认无用后主动删除 |
| `sync/upstream-<版本>` | 从 `dev` 创建，合入 `main`，完成适配与验证后合回 `dev` | 合并后允许保留，由用户确认无用后主动删除 |
| `release/<版本>` | 从 `dev` 创建，进行发布准备、修复和验证 | 保留，便于追溯 |

同步分支名称中的版本指上游正式版本，发布分支名称中的版本指我们自己的产品版本。

分支集成统一使用 Merge，保留提交历史，不使用 Rebase 或强制推送改写共享历史。不自动清理功能分支和同步分支；合并完成不等于授权删除。

## 功能开发

1. 从当前 `dev` 创建功能分支。
2. 在功能分支完成开发和相关验证。
3. 合并前如 `dev` 已有更新，先将最新 `dev` 合入功能分支，处理冲突并验证。
4. 将功能分支合回 `dev`。

同步上游不是每次功能合并的前置条件。

## 同步上游

仅同步上游正式发布的版本，不持续跟踪开发分支最新提交。同步由用户主动安排，通常在间隔一段时间、上游有较大版本更新时进行，不设置自动或高频同步。

1. 获取用户选定的上游正式版本，确认对应标签与提交，将 `main` 更新到该版本。`main` 不吸收我们的开发提交，不自动前进到上游最新开发位置。
2. 从当前 `dev` 创建 `sync/upstream-<版本>`。
3. 将 `main` 合入同步分支，在同步分支内解决冲突并适配变化。
4. 验证原有审查功能、我们的扩展及相关数据读取行为。
5. 如果期间 `dev` 有新提交，先将最新 `dev` 合入同步分支，再完成必要验证。
6. 验证通过后，将同步分支合回 `dev`。

未解决的问题留在同步分支处理，不将尚未通过验证的同步结果合入 `dev`。

## 扩展与冲突处理

- 尽量通过新增独立模块扩展功能，减少对上游原有文件的修改；必要修改保持集中，避免无关重构和整文件格式化。
- 优先复用上游能力，不为避免修改原文件而复制整套实现。
- 以新版上游实现为基础，保留上游更新，让我们的扩展适配新接口和行为，同时保留所需功能。
- 不将旧代码原样贴回，也不通过整批选择“我们的版本”或“上游版本”代替兼容性判断。
- 上游已有等价能力时，优先复用并减少重复实现；涉及功能取舍、无法同时保留双方预期行为时，先说明差异并由用户决定。
- 没有文本冲突也要检查行为兼容性，尤其是模型接口、会话数据和结果字段的变化。

功能设计应说明用户可见行为、关键约束和修改上游代码的理由。每次同步只记录重要冲突的位置、需要保留的行为、适配决定和验证结果，不维护上游功能流水账。记录优先放在同步 PR 描述中；没有 PR 时写入对应合并提交说明。

## 发布维护

1. 从 `dev` 创建 `release/<版本>`，只进行该版本的发布准备、修复和验证，不混入新功能。
2. 验证完成后，在最终提交上创建我们产品的版本标签，从该标签构建发布产物。
3. 发布分支中的修复通过 Merge 合回 `dev`，不合回跟踪上游的 `main`。
4. 发布分支和发布标签保留，发布标签不移动或覆盖。

## 文档维护

用户调整分支职责、同步策略、合并方式或保留规则时更新本文。具体功能设计放在项目设计中，单次冲突处理放在对应 PR 或提交说明中，不在本文积累开发流水账。
