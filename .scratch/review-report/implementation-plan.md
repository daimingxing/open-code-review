# 审查与报告功能实施协调计划

本计划供主线程智能体协调完成全部工单；它规定执行方式，不替代 Spec，也不表示已经启动开发。

## 目标与资料入口

完成[功能 Spec](spec.md)及[工单索引](README.md)中的 01–09，并在 `feature-review-report` 功能集成分支完成整体验收。范围和验收条件以 Spec 与各工单为准，依赖关系以工单索引及各工单的 Blocked by 为准。实施分支或工作树不能替代最终交付目标；集成使用 Merge 并保留已有历史。

启动前读取仓库生效的 AGENTS 约定、[项目设计](../../project-docs/project-design.md)、[分支维护](../../project-docs/branch-maintenance.md)、[领域术语](../../GLOSSARY.md)及 Spec 引用的 ADR。涉及上游行为时读取 [OCR 知识库](../../project-docs/open-code-review/README.md)，真实效果测试使用[资源索引](../../project-docs/review-resources.md)，开发复测记录遵循[复测目录约定](../../project-docs/retests/README.md)；供用户亲自验收的材料归入[人工验收目录](../../project-docs/mock/README.md)。

## 主线程的职责

主线程负责调度、契约协调、审查安排、集成与最终验收。每张工单交给新的实施子智能体，或能够共享仓库与持久化记录的独立会话；不要求一个实施上下文连续承担九张工单。派发使用文件和提交引用，不复制完整聊天历史。

主线程保留工单完成情况、执行者、分支或工作树位置、集成提交、关键决策和阻塞摘要。源码探索、完整日志和具体实现留给执行者；关键事实写回工单，不能只留在消息中。

收到完成全部工单的执行指令后，主线程按依赖连续推进，无须逐张等待用户确认。例行测试失败、合并冲突和实现细化由智能体处理；需要改变已确认的产品行为或缺少无法自行补齐的外部条件时，按下文的阻塞规则处理。

## 启动与调度

1. 核对当前分支、工作区改动、Spec、工单及已有执行证据；不要因索引写着“未实施”就忽略其他会话已经完成的工作。
2. 按分支维护约定，从已确认的 dev 基线建立或复用本功能的集成分支。先保证本计划、Spec 和工单能被实施工作树读取，不能让新工作树遗漏尚未提交的设计资料；保留用户已有改动，不使用重置或清理覆盖它们。
3. 选择前置工单已验收且已集成的任务，派发新的实施智能体。01、02 依次完成；02 后的 03、04、05 可并行，06 等待三者全部完成；随后依次推进 07、08、09。
4. 并行前确认 02 的共享材料契约，划清修改职责。预计同时修改相同核心逻辑且难以隔离时，顺序实施即可，不为并行增加抽象或额外流程。
5. 工单完成后检查证据，按风险安排独立审查，解决阻塞问题后集成并执行受影响检查。只有验收与集成都完成，才能解锁下游。

## 实施智能体的交付

每个实施任务包含工单入口、集成基线提交、工作树位置、相关契约及本次修改边界。实施者在自己的分支和工作树中完成任务；并行时不得共用同一可写工作区。当前工具无法派发时，明确说明限制，不冒充已创建独立执行者。

每次派发明确要求实施者读取并使用 [implement](../../.agents/skills/implement/SKILL.md)，执行范围仅限当前工单。按该 Skill 完成适用的测试、审查和提交，不递归协调全部工单。01 以配置和真实效果验收为主要交付，不为套用 TDD 增加无必要的产品代码；涉及代码实现时在已确认的测试边界使用 TDD。

实施者应做到：

- 读取工单与必要上下文，确认其前置条件；复用现有能力，交付本工单完整用户路径及对应测试。
- 使用仓库规定的检查入口。可控模型测试不替代 01 的真实模型知识应用验收；记录指定测试仓库的实际范围、版本及结果。
- 将开发者可复用的命令、运行前提、预期结果和实际验证状态写入 project-docs/retests 对应主题；用户验收脚本和稳定测试输入归入 project-docs/mock。
- 提交前遵守仓库审查要求；交付前合入最新功能集成分支，按影响复测。合并使用 Merge，不重写共享历史。
- 只对已满足的验收项打勾。交付未完成时说明剩余问题，不能将“代码已写”“命令返回成功”或“模型没有报错”当作完整验收。

派发指令可直接采用下面的文字，并补齐工单及工作树信息：

> 读取并使用 `.agents/skills/implement/SKILL.md` 实施本次指定工单。读取仓库约定、Spec、相关 ADR、工单和前置交付证据，确认工作树基于指定集成提交。完成本工单的行为、适用的测试与审查、提交及复测记录，不执行其他工单或递归协调全部任务。按实施协调计划在工单中记录交付、证据和下游注意事项；如需改变已确认的产品行为，先说明具体取舍。完成后返回简短摘要、分支与提交、工单记录和复测入口，保留未解决事项。

## 工单记录与上下文交接

沿用[分诊状态](../../project-docs/agents/triage-labels.md)，不把 Status: ready-for-agent 改成未定义的运行状态。执行者在工单追加“执行记录”，主线程维护其中的验收与集成结论；讨论仍按[工作事项约定](../../project-docs/agents/issue-tracker.md)写入 Comments。

每张工单的执行记录包含：

- 执行者或会话标识、工作树与分支、基线及交付提交。
- 当前进展、已完成验收项、剩余工作与阻塞原因。
- 测试命令或复测链接、测试版本、实际结果，以及未运行的检查和原因。
- 审查结论或无需独立审查的理由、修复情况、主线程验收结论和集成提交。
- 下游需要了解的共享契约、限制和重要取舍；没有额外事项时简短说明即可。

“工单完成”必须同时具备验收通过与已集成的记录。未集成的完成声明不能解锁依赖；工单文字也不能替代检查实际提交。

上下文不足、会话中断或需要更换执行者时，先记录当前提交或尚未提交的改动位置、已运行检查与下一步，再交给新上下文。主线程恢复时读取工单记录并核对 Git 状态，避免重复派发或覆盖仍在进行的工作。

## 独立审查与集成

按需让独立审查智能体检查工单差异、Spec 和验收证据。重点覆盖 02 的共享材料与原生兼容边界、06 的三模式整合，以及 07–09 的事实校验、安全展示与完整交付；其他工单根据改动风险决定，不强制每个文档改动都另起审查任务。

审查者不能只复述实施者的总结。阻塞问题交回实施者修复，主线程确认对应检查通过后串行集成；并行实现不意味着并行修改集成分支。若修复超出当前工单或改变公共契约，先评估已完成及在途工单的影响。

全部工单集成后，对整体差异做独立审查，并按 Spec 完成整体验收。测试必须针对实际待交付的集成版本；合并冲突解决或后续修复改变行为时，补跑受影响检查。

分支保留、工作树清理、合入 dev 和发布依照仓库约定及实际执行授权处理。完成开发不自动等于授权删除分支、强制推送或发布版本。

## 阻塞与完成条件

出现以下情况时记录具体阻塞、已尝试的方法和所需用户输入：必须改变已确认行为；缺少模型凭据或可用服务；指定资源不可访问；必须突破既有授权才能继续。仅暂停受影响的依赖路径，有其他满足条件的任务时继续推进，不能用替身结果代替缺失的真实验收。

最终交付需要：9 张工单的验收与集成证据齐全，Spec 的整体验收完成，独立审查中的阻塞问题已处理，可复测命令及前提已保存。主线程向用户提供集成分支与提交、完成范围、验收证据、复测入口、产物位置及剩余限制；有阻塞或未验收内容时如实报告，不能宣称全部完成。

## 给主线程的启动指令

> 本计划仅记录本次审查与报告功能的实施协调过程。后续功能不沿用本计划中的工单编号；开发复测记录写入 project-docs/retests，面向用户的验收材料写入 project-docs/mock。
