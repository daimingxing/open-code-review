## 结论与范围

提交已把 report 接入共享智能体循环，材料改为通过工具按需读取，并移除了旧的 HTML 内容检查和固定次数整份重试。方向符合本阶段要求，但模板迁移、执行失败处理和暂存清理存在遗漏，材料读取与压缩也缺少有效的集成验收。因此不能仅凭当前测试通过和工单勾选，判定全部完成。

本次收尾继续遵守已确认的边界：

- 复用 review 的模型运行配置、上下文容量、压缩阈值、压缩任务及停止机制，不另建 report 专属实现。
- 提示词优先引导读取报告 JSON、模板和样式等资源，避免重读代码；不增加源码访问权限拦截。报告事实不足应推动完善 review 阶段的 JSON 材料。
- 第一阶段不对 HTML 结构、事实、标签、脚本、样式、外部资源或视觉效果增加检查、清洗、修复与拒绝交付规则。
- 保留 JSON 输入校验、文件防覆盖、原子发布、取消与失败处理。执行结果判断不属于 HTML 内容审查。
- 修复以现有职责边界内的最小改动完成，不新增草稿恢复系统、通用文件系统抽象或独立上下文管理。

优先处理第 1–5 项。第 6 项顺手整理，不作为独立的功能阻塞项。第 1 项在首次审查中标为 P1；对照用户的第一阶段目标，调整为 P2：这是明确的提示契约冲突，但目前没有证据证明它必然阻止报告生成。

## 1. 模板仍描述已经移除的样式补充流程（P2）

### 问题与影响

`internal/report/templates/review-summary.md:22` 仍声明“应用会添加样式和报告交互”，并要求模型不要输出 `<style>`、行内样式、脚本等内容。第 25 行还沿用旧的事实、安全和完整性通过标准。

新流程在 `cmd/opencodereview/report_cmd.go:261` 将模板暂存给智能体读取，最后在第 201 行通过 `report.DeliverHTML` 保存智能体提交的原文，不再补充样式与交互。模型如果遵守旧模板，就可能只生成内容结构，而用户收到的报告也缺少相应样式和交互。

这不是审美是否达标的问题，而是模板承诺的应用行为已经不存在。模型也可能自行补全，因此不能把缺少样式说成所有生成结果必然发生的故障。

### 修复要求

- 检查单份、多份报告使用的模板、系统提示词和相关说明，清理旧流程遗留的冲突要求。
- 明确智能体负责生成可直接打开的完整 HTML，自行组织所需样式和交互；样式文件是可读取的参考资源，不承诺由应用自动插入。
- 删除为旧流程服务的样式、脚本禁令，以及“应用会补充”“程序会进行事实或安全验收”等失效说明。
- 保留 JSON 作为事实来源、按需读取素材和避免重复审查代码的提示引导。
- 不恢复 HTML 解析、样式注入或脚本检查，也不固定 DOM、控件、CSS 和布局。

### 验收

模板与系统提示词不再对生成职责发出冲突指令。可控模型提交包含自选样式或交互的 HTML 时，程序按原文保存，不因这些内容拒绝交付。测试无需把任何特定样式或脚本设为必需内容，也不以美观程度判定本次完成。

## 2. 循环提前停止后仍发布草稿并返回成功（P2）

### 问题与影响

`cmd/opencodereview/report_cmd.go:190–206` 只要发现调用过 `write_html`，即使 `completed` 为 false，也只输出警告，随后发布 HTML 并返回 nil。

智能体可能先提交初稿，再继续读取或修改。如果之后因压缩失败、轮数耗尽或其他共享循环停止条件而没有完成任务，当前命令仍向调用方报告成功。“写过草稿”被误当成了“完成任务”，自动化调用和用户都无法可靠区分。

### 修复要求

只在共享循环确认完成且已经提交 HTML 时发布最终报告。沿用共享循环的停止结果和原因，不另建一套停止状态机。

| 执行结果 | 预期行为 |
|---|---|
| 循环完成，已提交 HTML | 发布报告，返回成功 |
| 循环完成，未提交 HTML | 返回明确错误，不发布报告 |
| 循环提前停止，即使已提交草稿 | 返回错误并说明停止原因，不发布最终报告 |
| 模型调用失败或用户取消 | 返回对应错误或取消结果，不发布最终报告 |

本次不增加草稿导出或恢复功能。失败不得覆盖已有目标文件，不得破坏原始报告 JSON。

### 验收

补充“先写草稿，再提前停止”的命令级回归测试，断言非零结果、可识别的停止原因和最终文件不存在。保留正常完成、未写入 HTML、模型失败与取消的覆盖。

## 3. 材料读取和共享压缩的验收没有覆盖真实运行路径（P2）

### 问题与影响

`cmd/opencodereview/report_cmd_test.go:50` 的材料读取测试调用 `file_read` 读取不存在的 `ignored.json`，后续可控模型没有校验工具响应，直接提交预制 HTML。即使材料读取失败，测试仍可能通过。

同文件第 503 行的压缩测试只读取共享模板，检查 `MaxTokens`、压缩消息和工具调用上限等配置非空，没有运行 report，也没有触发压缩。

这两项属于证据缺口，不直接证明生产功能不可用。它们目前无法支持工单中“多轮读取材料”和“报告沿用实际压缩路径”均已验收的声明。共享循环自身的压缩单元测试也不能替代 report 集成路径验证。

### 修复要求

材料读取测试应从命令提供的路径中取得真实暂存文件，调用实际工具读取 JSON、模板和样式，检查工具响应成功且含预期内容，再由可控模型提交 HTML 并正常结束。材料读取失败应使测试失败，而不是被后续预制响应掩盖。

压缩测试应通过可控模型响应驱动 report 的实际循环达到共享阈值，确认调用现有压缩任务，并验证压缩后仍能继续调用工具、提交 HTML 和结束任务。使用隔离配置及共享机制允许的测试方式，不新增 report 专属阈值、压缩任务或重试逻辑。稳定上下文的保留方式沿用共享循环，不在 report 中复制实现。

测试可以在隔离范围内降低本次 report 实际使用的共享 `Template.MaxTokens`，或通过工具结果增加对话长度；配置恢复和测试相互隔离必须可靠。应验证压缩真正发生，而非仅达到警告线；目标是压缩成功后继续完成，不是触发 `StopCompression`。不能只另建一个未被 report 使用的 runner 来代替验证。

### 验收

- 测试证明模型确实收到本次暂存材料，而非仅证明工具名称存在。
- 测试证明 report 实际触发并完成共享压缩，随后继续执行成功，而非仅检查配置存在。
- 可控模型测试不依赖真实服务、凭据或固定自然语言措辞。
- 执行记录区分自动测试、浏览器观察和真实模型效果验证，不以其中一项替代另一项。

## 4. 暂存失败时目录清理使用了被清空的返回变量（P2）

### 问题与影响

`cmd/opencodereview/report_cmd.go:216–225` 的 `stageReportResources` 使用具名返回变量 `stageDir`，延迟清理闭包也引用该变量。创建目录后，后续错误分支以 `return "", ...` 返回，Go 会先将 `stageDir` 赋为空字符串，再执行延迟清理。

因此 `os.RemoveAll(stageDir)` 实际收到空路径，原暂存目录留在磁盘。若 JSON 已写入、模板或样式暂存失败，还会留下报告材料副本。调用方在该函数返回错误后直接退出，不能靠外层正常清理补救。

### 修复要求

清理闭包捕获创建成功后的固定目录路径，避免受返回变量赋值影响。保留成功返回后由调用方负责生命周期清理的边界，不重复构造另一套暂存管理。

### 验收

增加一个覆盖创建目录后暂存失败的回归测试，确认原目录和已写入材料被删除。失败场景应可重复，不依赖只在某个操作系统有效的权限技巧。若必须增加测试接缝，保持局部且最小，不为此引入通用故障注入框架。正常结束、模型失败和取消的清理行为也应保持正确。

## 5. 浏览器复测仍强制要求旧版控件和 HTML 限制（P2）

### 问题与影响

`project-docs/retests/html-report/verify-browser-report.cjs:42` 等位置寻找固定的 `report-filter-*` 控件，第 34 行还检查并拒绝脚本等元素。新的模型产物不保证这些 DOM，也不再由应用补齐旧版控件。

本次实际运行提交文档提供的复测入口，材料生成测试通过，但浏览器在等待 `#report-filter-unit-all` 时超时失败。这证明复测入口与新设计不一致，不能据此认定报告内容不合格，更不能为了通过测试重新要求固定控件或禁用脚本。

### 修复要求

- 移除或调整依赖旧版固定 DOM、筛选器、CSS 和脚本禁令的断言。
- 将本阶段必跑自动验收聚焦在工具执行、文件交付、退出状态和清理行为。
- 浏览器用于人工观察真实产物时，应明确观察用途，不把未确定的展示形式变成通过条件。
- 如果当前没有适合本阶段的自动浏览器断言，可以将旧脚本从必跑入口移除，并同步更新复测说明、调用入口及失效引用。历史验收证据保留。

### 验收

现行文档中的必跑复测命令能够完成，且不再因为缺少指定控件或含有自选脚本而判失败。文档准确说明验证范围，不宣称已经证明视觉质量或浏览器安全性。

## 6. 新增英文注释未遵守项目约定（P3）

### 问题与影响

例如 `internal/tool/write_html.go:13` 起的新增接口注释使用英文，部分报告交付代码也有同类情况。当前项目明确要求文档和代码注释使用中文，技术名称保持原文。

此项不影响运行，不应单独阻塞功能交付。

### 修复与验收

顺手将本次新增且必要的注释改为中文。删除只复述代码、没有额外上下文的注释；保留解释接口职责、草稿生命周期和文件发布约束的内容。不扩大为全仓库语言清理。

上游 `AGENTS.md` 要求源码使用英文，`make english-check` 也会拒绝未标记的中文；但本项目用户明确要求中文代码注释，不能据此改回英文。检查脚本已有逐行例外：含中文的必要注释行追加 `// allow-non-english: 用户要求中文代码注释`。现有 `internal/report/material.go` 已采用此方式。多行注释中每个含中文的行都需要标记，不能只在段首标记。

沿用这个已有机制，同时满足中文要求和现有检查。不修改全局英文检查规则，不新增目录级豁免。验收时运行 `make english-check` 及仓库适用的必要检查；无法运行的检查应如实记录环境限制。
